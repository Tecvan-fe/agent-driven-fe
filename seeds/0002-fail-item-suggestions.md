# 种子 0002:为 fail 项生成改进建议

> 源自终态主题"跨技术栈工程化健康度审查/优化工具"的第二颗种子。0001 只回答"哪些检查没过";这颗回答"没过的怎么办"。它挂在 0001 钉死的两个接缝上——checker 可插拔、report 结构化契约——不改内核。字段格式见 [`TEMPLATE.md`](./TEMPLATE.md)。

---

## 意图

在 0001 的审查报告基础上,为每一条 `status === 'fail'` 的检查附一条改进建议:告诉使用者这条为什么没过、该往哪个方向修。审查工具从"只报状态"进一步到"报状态 + 给方向",但仍只读、不动手改被审仓库。

## 边界

- **建议由谁产出**:改进建议的内容与每条 checker 强绑定——一条 checker 最清楚"自己这条为什么会 fail、该怎么修"。因此建议逻辑挂在 checker 侧,不新起一个游离于 checker 之外的"建议引擎"。这是为了守住 0001 接缝一(checker 可插拔):新增一条 checker 时,它的检查逻辑和它的建议逻辑一起进来,不需要在别处再改一处。
- **只读不变**:延续 0001 铁律,工具绝不修改被审仓库、不发网络请求、无副作用。**本颗种子不做"自动向被审仓库提修复 PR"**——那是 0001 圈外明列、留给更后面的能力,这里只产出文字建议,不产出改动。
- **只针对 fail**:`pass` 与 `not-applicable` 的检查不产建议(前者无需修,后者不适用)。建议只挂在 fail 项上。
- **不改评分**:总分口径沿用 0001 的 `passed / applicable`,建议是报告的附加信息,不参与算分、不改变 `score` 的既有形状。
- **不引额外技术栈 / 不引 Web UI / 不做多语言文案**:沿用 0001 的 TS + Node + Vitest + GitHub Actions,建议文案为中文单一语种即可,不为国际化预留框架。
- **圈外**:自动修复、修复 PR、建议的优先级排序算法、跨 checker 的聚合建议(如"这几条一起说明项目缺 CI")、把建议接入外部 LLM 生成——都不在本颗。本颗只做"每条 fail 各自给一条静态可判定的建议"。

## 成功标准

1. 对一个含 fail 项的样例仓库运行 CLI,报告里每一条 `fail` 检查都带上了对应的改进建议;`pass` 与 `not-applicable` 项不带建议。
2. 建议随对应 checker 一起定义——新增一条 checker 时,它的建议逻辑在同一处给出,不需要改动扫描/报告骨架。
3. JSON 输出与人类可读输出都能体现建议;两种格式对同一条 fail 的建议表达一致。
4. 沿用 0001 的三个 fixture 验证:全绿仓库报告中无任何建议;全红仓库三条 fail 各带一条建议;非 TS 仓库的 strict 项为 not-applicable、不带建议。
5. 建议内容与检查项匹配——lint 缺失的建议指向 lint、测试缺失的建议指向测试、strict 未开的建议指向 strict,不出现张冠李戴。

## 验证器声明

- **成功标准 1 / 4(fail 才带建议、三 fixture 行为)**:Vitest 对三个已有 fixture 断言——遍历报告,凡 `status==='fail'` 的项其建议字段非空、其余项无建议字段(或为空)。判据:`pnpm test` 通过,CI 绿。
- **成功标准 2(建议随 checker 定义、不动骨架)**:分两层。自动层:类型上建议字段进入 checker 的产出契约,`tsc` 保证每条 checker 都遵守;一个测试证明新增一条会 fail 的 checker 后,其建议能出现在报告里,无需改 scan/report。人工层:"未改动扫描/报告骨架"由人在 PR diff 上确认(同 0001 接缝一的人工判据)。判据:自动层测试 + tsc 通过;人工层 PR review 记录。
- **成功标准 3(双格式一致)**:测试断言 JSON 里 fail 项的建议字段与人类可读摘要里渲染出的建议文本对应同一来源,不各写一份。判据:对应测试通过。
- **成功标准 5(建议与检查项匹配)**:测试对全红 fixture 断言每条 fail 的建议文本含其检查项的关键指向(如 lint 项建议提到 lint 配置)。判据:对应测试通过。
- **贯穿验证器(CLAUDE.md 铁律 1)**:本颗种子及其实现全程走 `分支 → PR → 合入 main`,不直推。判据:改动以 PR 形式出现在 git 历史中。

## 给推进者的话(欠定义点,留给需求/设计阶段解决)

本颗种子的意图和边界是清楚的,但**成功标准里有意留下几处没有一次性钉死的问题**,需要在需求梳理与设计阶段通过启发式推导来收敛。推进时应主动把这些问题显式提出、给出取舍理由,而不是随手默认:

1. **建议落在 report 契约的什么位置?** 0001 的 `CheckResult` 是 `{ id, status, evidence }`。建议是给 `CheckResult` 增一个可选字段(如 `suggestion?: string`),还是在报告顶层另开一个建议数组?哪种对 0001 的 report 结构化契约冲击最小、对后续种子最友好?需要在设计里论证并选定。
2. **建议是纯文本,还是要带结构**(如"问题短句 + 修复动作 + 可选文档链接")?更结构化意味着更早引入复杂度。要判断当前这颗种子是否值得,还是先用一句话文本、把结构留给真有需求时再加——这里正是"够用就好 vs 提前设计"的取舍点,不要默认往复杂了做。
3. **建议文案写死在 checker 里,还是抽一层文案管理**?单语种、三条 checker 的规模下,抽象文案层是不是过度设计?
4. **fail 但拿不到足够上下文时**(如确实无 lint 配置,建议能给得很具体;但某些 fail 的 evidence 信息有限),建议要不要有兜底表达,避免出现空洞的"请修复此项"?

这些问题没有唯一正确答案,取舍取决于"这颗种子的边界内够不够用"。推进者要做的是:识别出这些欠定义点 → 给出有理由的判断 → 把判断写进需求/设计文档,而不是追着把每一种未来可能都提前设计进去(那会滑向过度设计,越出本颗种子的边界)。
